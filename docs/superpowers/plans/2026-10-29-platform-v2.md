# ArcBox Platform v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make ArcBox able to host a persistent, week-to-week campaign game. Players pick who they are in the room (one tap the following week). Campaigns survive restarts, and rooms come back after one with the same code. Games can drive their own phone screens. The TV downloads content from the server and can tell a game when an animation has finished.

**Architecture:**
- **Storage:** a SQLite database (`Microsoft.Data.Sqlite`, no ORM) behind a background writer that combines writes per key. It holds profiles, profile keys, room records and campaigns.
- **Profiles and campaigns:** in-memory services that read synchronously, so the room actor can use them without risking the watchdog.
- **The room actor:**
  - offers seats to phones (`Peek`/`TakeSeat`);
  - in campaign games, checks the campaign out and hands the game an `ICampaignLease`;
  - persists its membership, never its game state, so it can be rebuilt after a restart.
- **The phone (`web/play`):** per-game modules loaded lazily (skin, custom screens, portal).
- **The TV (`Host.Core`):** a content cache keyed by pack hash, and a channel for sending signals to the game.

**Tech Stack:** .NET 10 (ASP.NET Core, SignalR, System.Text.Json), `Microsoft.Data.Sqlite` 10.0.x, xUnit v3, `FakeTimeProvider`; Vite, TypeScript, Preact and Vitest 4 for the phone; Godot 4.7 .NET for the TV shell.

**Spec:** [`docs/superpowers/specs/2026-10-29-platform-v2-design.md`](../specs/2026-10-29-platform-v2-design.md). The section references below (§) point into it. Mockups: [`docs/superpowers/mockups/tactics/06-phone-join.png`](../mockups/tactics/06-phone-join.png).

**Issues:** this plan closes #23 (Task 12) and #24 (Task 16). #25 (REDLINE host-signal pacing) is optional follow-up work after Task 9.

## Global Constraints

- **Dependencies:**
  - `ArcBox.Sdk` and `ArcBox.Sdk.Testing` still reference only the BCL.
  - `Microsoft.Data.Sqlite` `10.0.*` is added to `ArcBox.Server` only.
  - No ORM. No new npm dependencies.
- **Build:** `TreatWarningsAsErrors`, nullable and implicit usings everywhere, as now. New public SDK types get XML doc comments in the style of `ControllerView.cs`.
- **Secrets at rest:** player secrets, host tokens and profile keys are stored **only** as `Secrets.Hash(value)` (SHA-256, base64url) and compared with `CryptographicOperations.FixedTimeEquals`. Plaintext exists only in the response that issues it.
- **Formats and lengths:**
  - New tokens (seat secrets, host tokens, profile keys): `Secrets.NewToken()` (128-bit, base64url).
  - Profile IDs: `pr_` followed by 16 base64url characters.
  - Campaign codes: 4 letters from `BCDFGHJKLMNPQRSTVWXZ` (the room-code alphabet), unique among campaigns.
  - Campaign names: trimmed, 1–32 characters. Seat and member names: the existing 1–12-character rule.
- **Limits** (exact):
  - 10 profile keys per profile (newest kept);
  - 8 members per campaign; 20 campaigns owned per profile;
  - 2 MB per campaign document; 50 snapshots per campaign, plus an autosave snapshot at most every 10 minutes;
  - `CustomView` data 64 KB (warning only);
  - host signal: `kind` matches `^[A-Za-z0-9_.-]{1,32}$`, payload at most 4096 bytes;
  - `RoomOptions.RetainFor` 24 h; content cache keeps the newest 3 hashes per pack;
  - storage writer flushes every 250 ms or at 64 pending operations; health is degraded when the oldest pending write is older than 10 s;
  - backups daily at 04:00 UTC, keeping 14; portal API limited to 60 requests per minute per IP.
- **User-facing strings** (exact; `{…}` is substituted):
  - "Someone's already playing as {Title}."
  - "Pick a seat or enter a name."
  - "Game in progress, join after this round." (existing)
  - "Couldn't rejoin. Please join again." (existing)
  - "Room not found." (existing)
  - "This game doesn't use campaigns."
  - "Campaign not found."
  - "{Name} is being played in room {CODE}."
  - "This campaign has {n} members; rooms hold 8."
  - "Campaign names are 1–32 characters."
  - "You already own 20 campaigns."
  - "This campaign is full (8 members)."
  - "That name is taken." (existing)
  - "Pick a campaign first."
  - "Everyone needs to pick who they are first."
  - "You can only change who you are in the lobby."
  - "Only the VIP can create a campaign."
  - "A session is in progress. Use the in-game menu."
  - "Game interrupted: the server restarted."
  - "Game interrupted: the room was idle."
  - "Only the host can do that." (existing)
  - "Invalid signal."
  - "This screen needs a newer app"
  - "Reload"
  - "Pick yourself in a session first"
  - "Loading content… {n}%"
- **Compatibility:**
  - The hub's `Join(code, name)` and `Rejoin(code, playerId, secret)` keep their signatures.
  - The existing `/healthz` still answers `ok` when healthy.
  - REDLINE's server, phone and TV behavior is unchanged except where the spec says otherwise (seat swapping, interrupted note).
- **Plan decision (spec §3.2 lets either host or VIP create):** `CreateCampaign` is **VIP-only**, because the creator becomes the owner and must be a profile with a phone. The host only selects campaigns.

## Review Focus

These are the five failure modes most likely to bite real players that the main tests don't naturally exercise. Each has a pinned test in the task in brackets.

1. **Two phones tap the same offline seat at the same moment.** Exactly one wins; the other gets "Someone's already playing as {Title}." and a fresh `Peek`. [Task 4]
2. **A phone whose seat was taken by another phone comes back.** Its stored secret fails `Rejoin` once, and it lands on the picker rather than retrying in a loop. [Task 4 server, Task 13 phone]
3. **The server stops while writes are still queued.** A `TakeSeat` immediately followed by shutdown is still in the room record after the rebuild. [Task 8]
4. **A parked room's campaign is picked up by another room, then the first room is rebuilt.** The rebuilt room can't check the campaign out, so it returns to the lobby with "{Name} is being played in room {CODE}." instead of resuming twice. [Task 8]
5. **A portal command races a session start.** If a room checks the campaign out between the phone loading the portal and submitting a command, the command gets `409` with "A session is in progress. Use the in-game menu." and the document is unchanged. [Task 5, Task 7]
